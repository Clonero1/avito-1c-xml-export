# Правила для Codex и агентов

## Язык и стиль

- Проект ведётся на русском языке.
- Не переводить бизнес-термины на английский без необходимости.
- Не удалять бизнес-контекст: склады, тип цен, имена реквизитов, ограничения Авито и сценарии работы важны для разработки.
- Не менять смысл ТЗ без явного комментария в документе или отдельного раздела `Примечание`.

## Markdown

- Все XML-примеры писать только в fenced code blocks с языком `xml`.
- Не оставлять XML-теги обычным текстом вне блока кода.
- CSV-примеры писать в fenced code blocks с языком `csv`.
- Код 1С писать в fenced code blocks с языком `bsl`, если он находится в Markdown-документах.

Пример XML:

```xml
<Ad>
  <Id>RS-00180081</Id>
</Ad>
```

## Код 1С

- Код 1С писать в стиле BSL.
- Использовать русские имена процедур и функций, если это соответствует контексту обработки.
- Черновые места отмечать как `TODO`.
- Не выдумывать точные имена регистров ERP 2.5, если они не подтверждены в конфигурации.
- Для спорных имён объектов 1С указывать варианты и пометку `TODO: уточнить в ERP 2.5`.

## Архитектурные правила

- Не считать проект готовым, пока нет `.epf` или исходников обработки, пригодных для сборки.
- Не генерировать весь XML с нуля на первом этапе.
- Сохранять подход: текущий рабочий XML Авито используется как шаблон.
- Старые объявления нельзя молча переводить на новые `Id`, чтобы не создать дубли на Авито.
- Новые объявления могут использовать `Id = Код 1С`, если это согласовано.

## Спорные решения

Любые спорные решения выносить в раздел `Вопросы` или в файл [open_questions.md](./open_questions.md).

К спорным решениям относятся:

- способ выгрузки фото на сервер;
- хранение таблицы соответствий;
- автоматическое создание новых объявлений;
- сопоставление артикулов с суффиксами, например `3918776RN` и `3918776`;
- определение контактного лица;
- определение адреса объявления.
